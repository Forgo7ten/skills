# Git Commit 规范

## 1. 基本约束

默认语言：中文。

-   所有提交信息必须使用 Conventional Commits 格式。
-   Scope 可选，不强制要求填写。
-   不设置 description 的固定字符数限制，但必须保持简洁。
-   提交信息必须以实际代码变更为依据，不得仅根据需求描述或开发计划拟定。

## 2. 提交格式

``` text
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

说明：

-   `type`：必填，表示变更类型。
-   `scope`：可选，表示受影响的模块或功能，使用圆括号，例如
    `feat(auth):`。
-   `!`：可选，表示存在不兼容变更。
-   `description`：必填，一句话概括本次提交的主要变更。
-   `body`：可选，补充变更原因、具体内容或影响。
-   `footer`：可选，记录关联问题或不兼容变更说明。

### Type 类型

  Type         含义       使用场景
  ------------ ---------- --------------------------------------
  `feat`       新功能     新增模块、界面、函数或能力
  `fix`        修复问题   修复崩溃、逻辑错误或异常行为
  `refactor`   重构       调整代码结构，不改变外部功能行为
  `perf`       性能优化   降低资源占用、提高执行效率
  `docs`       文档       更新 README、使用说明、注释等
  `style`      代码样式   调整格式、空白和代码风格，不改变逻辑
  `test`       测试       新增或修改测试用例
  `build`      构建       修改构建系统、构建工具或相关配置
  `ci`         持续集成   修改 CI 配置和自动化流程
  `chore`      其他维护   不属于以上类型的日常维护工作
  `deps`       依赖管理   新增、升级、降级或锁定依赖版本
  `revert`     回滚       撤销此前的提交

`deps` 为本规范额外约定的类型，用于单独标识依赖变更。

### Description 编写要求

-   使用一句话概括本次提交的主要变更。
-   简洁、准确地说明变更对象和结果。
-   优先使用明确的动作和对象，避免模糊表述，例如「更新了一些内容」「优化代码」。
-   不在标题中堆叠实现细节、变更原因或多个子任务的具体内容，相关信息放入
    body。
-   不记录开发过程、讨论过程或临时状态。

### Body 编写要求

Body 为可选内容，仅在有必要时填写。

可以补充：

-   变更原因。
-   具体实现内容。
-   重要的功能变化或影响。

不要重复 description，也不要记录开发过程或中间状态。

### Footer 编写要求

仅在有必要时填写，例如：

-   关联问题：`Closes #123`
-   不兼容变更：`BREAKING CHANGE: ...`

存在不兼容变更时，必须通过标题中的 `!` 或 `BREAKING CHANGE:` footer
明确标记，并说明影响。

## 3. 最终变更约束

**Commit message
必须客观描述本次提交实际形成的变更，不得记录开发过程中的中间方案或状态。**

具体要求：

1.  每个 commit
    应描述该提交实际引入的变更，不需要与之前的实现方案进行比较。
2.  某个方案被后续方案替换时，只描述最终采用的方案，不保留已经被替换的中间方案。
3.  多个 commit 压缩为一个 commit 时，必须根据合并后的最终 Diff 重新拟定
    message，不得直接拼接原有提交信息。
4.  不记录用户确认时间、讨论结论、开发过程或其他与最终变更无关的信息。

示例：

**分别提交时：**

``` text
commit1: xxx
commit2: 采用 X 方案实现 .. 功能
commit3: 采用 Y 方案实现 .. 功能
```

**将 commit2 和 commit3 压缩为一个 commit 时：**

``` text
commit1: xxx
commit4: 采用 Y 方案实现 .. 功能
```

**不推荐：**

``` text
commit1: xxx
commit4: 采用 Y 方案实现 .. 功能（不再使用 X 方案）
```

核心原则：只描述本次提交最终实现了什么，不描述它经历了什么。

## 4. 提交前检查

拟定 commit message 或执行 git commit 前，必须完成以下检查：

1.  已加载并遵循本 Skill。
2.  检查实际暂存区 Diff（`git diff --cached`），确认提交内容。
3.  根据实际变更选择正确的 type，scope 按需填写。
4.  description 准确概括主要变更，具体细节按需放入 body。
5.  检查是否存在中间状态、过程性描述或与最终变更无关的内容。
6.  存在不兼容变更时，确认已明确标记。

合并或压缩多个提交时，必须检查合并后的最终 Diff，并重新拟定提交信息。

未能加载本 Skill 时，不得继续拟定提交信息或执行提交。
